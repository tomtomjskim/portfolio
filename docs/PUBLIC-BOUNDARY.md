# 공개 범위

## 공개 가능

- 비식별화한 문제 정의와 업무 맥락
- TOM이 직접 판단·설계·구현·검수한 확인 범위
- AI·일반 코드·사람의 책임 분리
- 테스트·E2E·CI·수동 확인 등 실제 검증 방식
- 확인된 제한사항과 미검증 범위
- 공개 저장소·PR·CI 링크
- 비식별화한 구조도
- 공개 가능한 사례와 화면 구성용 자료
- 실제 UI Source에 합성 데이터만 주입한 검수 완료 화면
- 개인 운영 환경에서 사용했다는 제한된 사실

## 공개 금지

- 비공개 저장소명과 내부 경로
- 원본 AI 대화
- 고객·주문·결제·배송·생산 데이터
- credential·API key·token
- 내부 endpoint·hostname·설정값
- 상세 운영 로그·운영 화면 원본 캡처
- 운영 Domain·서버명·IP·Port·Backup 경로
- 실제 아이디어·Prompt·Raw Response·Token·비용·Session ID
- 보호 이력서 원천
- 면접 예상 질문·답변 스크립트·공격 질문·리허설 기록
- 회사별 지원 문안·Role Adapter·면접관 대응 메모
- Claim의 내부 상태표와 보류·제외 판단
- 검증되지 않은 생산성·시간·비용·정확도·SLA 수치
- 이력서·포트폴리오 근거에서 제외한 내부 자산
- 공개 연구·개발 자료를 이전 회사의 운영 소스로 표현
- 개인 실사용 프로젝트를 회사 실무·외부 상용 서비스로 표현

## 사례 분류 경계

```text
sanitized-actual-work
= 회사 실무를 공개 가능한 수준으로 비식별화

private-personal-product
= 비공개 개인 프로젝트를 합성 화면과 제한된 설명으로 공개

public-rnd
= 공개 코드·문서·CI로 확인 가능한 현재 개발 자료
```

세 분류는 서로 다른 근거 강도와 해석 상한을 가진다.

## 합성 화면 경계

합성 화면은 실제 UI Source와 Layout을 사용하되 API 응답과 표시 데이터만 Fixture로 대체합니다.

필수 표시:

> 포트폴리오 공개를 위해 합성 데이터로 재현한 화면

합성 화면이 증명하는 것:

- 실제 구현한 화면 구조와 사용자 흐름
- 입력·상태·행동의 관계

합성 화면이 증명하지 않는 것:

- 실제 운영 데이터
- 외부 사용자·사용량·성과
- 운영 Domain의 공개 가능성
- 비공개 Source의 독립 검증

## 판단 우선순위

```text
TOM의 최신 명시적 정정
→ 현재 확인된 GitHub 상태
→ 최신 공개 주장 범위
→ 경력 원천 잠금 문서
→ 과거 감사 보고서·원장
```

충돌할 때 과거 문서의 강한 상태를 자동으로 되살리지 않습니다.

## 웹사이트 반영 경계

```text
portfolio/main
→ 내용 검증
→ 정적 화면
```

GitHub Pages는 화면 계층입니다. 웹 문장과 원문이 다르면 `tomtomjskim/portfolio`의 `main`을 기준으로 맞춥니다.

웹 화면에는 다음만 노출합니다.

```text
소개
업무 사례
개인 실사용 프로젝트
공개 개발 자료
근거 링크
```

작업 방식 체크리스트, 면접 준비 자료와 내부 검수 메모는 웹 화면에 투영하지 않습니다.

## 공개 전 확인 질문

1. 이 문장은 실제 업무 사례, 개인 실사용 프로젝트, 공개 연구·개발 중 무엇인가?
2. TOM의 직접 역할이 원천보다 강해졌는가?
3. 측정하지 않은 수치가 추가됐는가?
4. 비공개 경로·데이터·endpoint·credential이 노출됐는가?
5. 면접 준비·지원 전략·내부 평가 자료가 섞였는가?
6. 계획·시제품·CI 통과를 완료된 운영 성과로 확대했는가?
7. 사례와 근거 문서의 한계가 서로 일치하는가?
8. 합성 화면이 실제 운영 데이터나 외부 사용자 증거처럼 보이는가?
9. 개인 프로젝트가 회사 실무나 상용 서비스로 오인될 수 있는가?
