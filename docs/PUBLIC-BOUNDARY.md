# 공개 범위

## 공개 가능

- 비식별화한 문제 정의와 업무 맥락
- TOM이 직접 판단·설계·구현·검수한 확인 범위
- AI·일반 코드·사람의 책임 분리
- 테스트·E2E·CI·수동 확인 등 실제 검증 방식
- 확인된 제한사항과 미검증 범위
- 공개 저장소·PR·CI 링크
- 비식별화한 구조도
- 공개 가능한 사례와 화면 구성용 자료

## 공개 금지

- 비공개 저장소명과 내부 경로
- 원본 AI 대화
- 고객·주문·결제·배송·생산 데이터
- credential·API key·token
- 내부 endpoint·hostname·설정값
- 상세 운영 로그·화면 캡처
- 보호 이력서 원천
- 검증되지 않은 생산성·시간·비용·정확도·SLA 수치
- 이력서·포트폴리오 근거에서 제외한 내부 자산
- 공개 연구·개발 자료를 이전 회사의 운영 소스로 표현

## 판단 우선순위

```text
TOM의 최신 명시적 정정
→ 현재 확인된 GitHub 상태
→ 최신 공개 주장 범위
→ 경력 원천 잠금 문서
→ 과거 감사 보고서·원장
```

충돌할 때 과거 문서의 강한 상태를 자동으로 되살리지 않습니다.

## 웹사이트 반영 경계

```text
portfolio/main
→ 내용 검증
→ 정적 화면
```

GitHub Pages는 화면 계층입니다. 웹 문장과 원문이 다르면 `tomtomjskim/portfolio`의 `main`을 기준으로 맞춥니다.

## 공개 전 확인 질문

1. 이 문장은 실제 업무 사례인가, 공개 연구·개발 자료인가?
2. TOM의 직접 역할이 원천보다 강해졌는가?
3. 측정하지 않은 수치가 추가됐는가?
4. 비공개 경로·데이터·endpoint·credential이 노출됐는가?
5. 계획·시제품·CI 통과를 완료된 운영 성과로 확대했는가?
6. 사례와 근거 문서의 한계가 서로 일치하는가?
