# 아이디어 발굴·검토·기획 자동화

## 핵심 질문

일회성 LLM 브레인스토밍을 반복 가능한 제품 흐름으로 바꾸려면, 무엇을 모델에 맡기고 무엇을 코드·상태·사람 판단으로 고정해야 하는가?

## 한눈에 보기

| 항목 | 내용 |
|---|---|
| 문제 | LLM 대화의 아이디어가 세션마다 흩어지고 비교·선택·후속 기획·실패 복구를 일관되게 관리하기 어려움 |
| 판단 | LLM은 리서치·아이디어·문서 초안을 담당하고, 일정·상태·비용·파싱·저장·복구는 코드로 관리하며 최종 선택은 사람이 수행 |
| 근거 | 개인 운영 환경의 실제 사용과 비식별화한 구현·Migration·실패 복구·검증 기록 |

## 문제

LLM으로 아이디어를 만드는 것 자체는 어렵지 않았습니다. 문제는 결과가 대화 단위로 흩어져 다음 작업으로 이어지지 않는다는 점이었습니다.

- 이전 아이디어와 중복되는지 비교하기 어려움
- 채택·보류·거절의 이유가 남지 않음
- 예약 실행과 수동 실행의 상태를 같은 기준으로 볼 수 없음
- 채택한 아이디어를 기획서와 설계 문서로 옮기는 작업이 반복됨
- 잘린 JSON이나 최대 Turn 종료가 발생하면 결과와 비용을 함께 잃을 수 있음

목표는 “좋은 사업 아이디어를 자동으로 판정하는 AI”가 아니라, **아이디어 후보를 생성하고 사람이 검토해 후속 산출물로 연결하는 개인 실사용 시스템**을 만드는 것이었습니다.

## 업무 환경과 제약

- 개인 운영 환경에서 사용하는 비공개 프로젝트
- LLM CLI와 웹 검색 결과는 매번 달라질 수 있음
- 예약 실행은 사람이 즉시 확인하지 못할 수 있음
- 실제 아이디어·Prompt·응답·비용·운영 환경은 공개할 수 없음
- 외부 사용자나 조직 도입 성과는 없음
- AI가 사업 성공 가능성을 확정할 수 없음

공개 포트폴리오에서는 실제 운영 화면이나 데이터를 사용하지 않고, 승인된 합성 데이터 화면과 비식별화한 구조만 사용합니다.

## 확인 과정

먼저 LLM이 잘하는 부분과 애플리케이션이 강제로 보장해야 하는 부분을 분리했습니다.

```text
복수의 합리적 결과가 가능한가?
→ LLM 후보

정확한 상태·형식·권한·재실행이 필요한가?
→ 규칙 기반 코드

사업·제품 선택처럼 책임이 필요한가?
→ 사람 판단
```

그다음 전체 흐름에서 다음 경계를 확인했습니다.

- 실행 조건과 분석 입력
- Session과 Idea 상태
- 채택·보류·거절의 변경 주체
- 기획서 Version과 후속 단계
- Token·Budget과 재시도
- LLM 응답의 구조 검증
- 실패 결과를 다시 사용할 수 있는 복구 경로
- DB Migration과 기존 데이터 Backfill

## 판단

책임을 다음과 같이 분리했습니다.

| 영역 | 담당 |
|---|---|
| LLM | 리서치, 아이디어 후보, 분석, 기획·설계 초안 |
| 규칙 기반 코드 | 일정, 상태, 인증, Budget, 파싱, 저장, 재시도, 복구, Migration |
| 사람 | 실행 조건, 채택·보류·거절, 후속 단계 진입, 최종 사용 |

LLM 점수만으로 아이디어를 자동 승격하지 않았습니다. 사람의 채택·거절을 상태 변경의 기준으로 두고, 거절 사유는 이후 생성 과정에서 참고할 수 있도록 별도 기록했습니다.

## 선택 기준과 대안

### 대화 기록만 유지

가장 단순하지만 아이디어 비교·상태·후속 기획·실패 복구가 다시 수작업이 됩니다.

### 모델이 자동으로 채택

처리량은 늘지만 사업·제품 선택 책임을 모델 점수에 넘기게 됩니다. 최종 결정은 사람에게 남겼습니다.

### 실패할 때마다 전체 재실행

구현은 단순하지만 이미 생성된 결과와 비용을 버리게 됩니다. 원본 응답 보존과 재파싱 경로를 우선했습니다.

### 처음부터 완전 자율 Workflow 구현

범위가 커지고 검증해야 할 상태가 급격히 늘어납니다. 실제 사용 중인 아이디어 생성·분류·기획 흐름을 먼저 안정화하고, Workflow·Run·Artifact·Decision 기반은 후속 확장으로 분리했습니다.

## 구현

### 실행과 분석

- Quick·Standard·Deep·Autonomous 실행 방식
- 카테고리·주제·출처 계층·분석 관점·평가 차원·목표 규모 설정
- 예약 실행과 수동 실행
- 실행 중 단계와 완료·실패 상태 표시

### 아이디어 검토

- 아이디어 목록·상세·비교
- 채택·보류·거절
- 거절 사유 선택
- 키보드 기반 빠른 분류
- 거절 결과의 Memory 반영 여부 분리

### 기획 산출물

```text
기획서 초안
→ 웹 검색 기반 보강
→ 구현 관점의 설계 문서
```

단계별 결과를 별도 Version으로 저장하고, 보강 단계가 실패하면 초안을 이용해 설계 단계로 진행할 수 있게 했습니다. 최종 문서는 Markdown과 PPTX로 확인할 수 있습니다.

### LLM 출력 복구

예약 실행에서 LLM이 최대 Turn으로 종료하며 부분 JSON을 반환하는 문제가 반복됐습니다. 문자열은 존재했지만 요구한 구조를 만족하지 않아 업무 결과로 사용할 수 없었습니다.

다음과 같이 변경했습니다.

- 출력 존재 여부와 의미적 유효성 분리
- JSON 구조가 유효하지 않으면 기존 Session 재개
- 파싱 실패 전에 원본 응답 보존
- 잘린 JSON과 trailing comma 복구
- LLM을 다시 호출하지 않는 수동 재파싱 경로
- 예약 실행 실패 시 제한된 재시도
- 실제 실패 형태를 반영한 파싱 테스트

```text
모델 응답 완료
≠ 애플리케이션 업무 완료
```

완료 기준을 모델 메시지가 아니라 검증 가능한 출력 구조와 저장 결과로 바꿨습니다.

## 검증과 실제 사용

- 개인 운영 환경에 배포해 실제 사용
- 단위 테스트·TypeScript 검사·정적 빌드·보안 및 품질 검사
- 임시 PostgreSQL을 이용한 Migration·Backfill·Rollback 확인
- 배포 전 Backup과 배포 후 애플리케이션·DB 상태 확인
- 인증되지 않은 API 요청 차단 확인
- Playwright 기반 기본 실행 경로 확인

공개 화면은 운영 환경을 직접 캡처하지 않고 합성 데이터로 재현합니다. 화면은 실제 UI Source를 사용하되 API 응답만 합성 Fixture로 대체합니다.

## 한계

- 비공개 저장소라 외부 독자가 전체 코드를 독립 검증할 수 없음
- 외부 사용자·조직 도입·매출 등 사업 성과가 없음
- 측정 가능한 생산성·정확도·비용 절감 수치를 제시하지 않음
- AI는 아이디어 후보와 문서 초안을 만들며 사업 타당성을 확정하지 않음
- Workflow·Run·Artifact·Decision의 백엔드 기반은 있으나 전용 Venture UI 완료를 주장하지 않음
